# PAYMENT RECOVERY AGENT — ANTIGRAVITY IDE MASTER BUILD PROMPT

## AI-Powered Payment Failure Triage & Revenue Recovery System

---

# 0. YOUR ROLE

You are the AI engineering partner inside Antigravity IDE helping me build an **AI-powered Payment Failure Triage & Recovery Agent**.

The system is designed to help merchants identify failed payments, determine whether they are suitable for automated recovery, diagnose the likely failure reason, execute safe recovery actions, and escalate risky or uncertain cases to a human.

The core product philosophy is:

> **Don't just tell the merchant that a payment failed. Determine why it failed, decide what should happen next, safely execute the recovery action, and prove the outcome.**

The product should move through this chain:

```
Payment Failure
      ↓
Risk Assessment
      ↓
Failure Diagnosis
      ↓
Recovery Decision
      ↓
Safe Action
      ↓
Outcome Verification
      ↓
Revenue Recovered / Human Escalation
      ↓
Audit Trail
```

The system must prioritize:

**Revenue Recovery + Safety + Explainability + Auditability**

Do not attempt to build a massive autonomous payment platform.

Build a controlled, verifiable recovery system first.

# 2. PROJECT CONTEXT

## Problem

Merchants lose revenue because payments can fail for many different reasons:

- insufficient funds,
- bank declines,
- temporary payment failures,
- timeouts,
- technical failures,
- payment-method issues,
- suspicious transactions,
- ambiguous payment states.

A merchant cannot treat every failed payment in the same way.

Some payments should be retried.

Some should receive a payment link or reminder.

Some should wait before another attempt.

Some should immediately be escalated for human review.

The system should automatically distinguish these cases.

---

# 3. PRODUCT NORTH STAR

The primary question the system must answer is:

> **"Given this failed payment, why did it fail, is it safe to recover automatically, what recovery action should be taken, and what happened after that action?"**

Every major screen and backend workflow should contribute to answering this question.

Avoid building a generic chatbot.

Avoid building a generic payment dashboard.

The system should prioritize:

**Action > Information**

Instead of:

```
Payment failed.
Reason: Bank decline.
```

The system should provide:

```
Payment Failed
₹4,999

Likely Cause:
Temporary bank decline

Risk:
LOW

Recommended Action:
Retry after 48 hours

Why:
Customer has 3 previous successful payments
and no suspicious activity was detected.

Action:
Recovery scheduled

Retry Limit:
1 / 3
```

# 4. CORE SYSTEM PRINCIPLES

These principles are mandatory.

## 4.1 Risk is deterministic

The risk classifier should be based on a deterministic ML/rule-based model.

Possible models:

- Logistic Regression
- XGBoost
- rule-based classifier

The model should output a risk score/classification.

The LLM must **not replace the risk model**.

---

## 4.2 LLM is an intelligence/explanation layer

The LLM can:

- diagnose failure context,
- explain decisions,
- summarize payment history,
- generate merchant/customer communication,
- recommend reasoning within allowed actions.

The LLM must not invent:

- payment status,
- customer history,
- transaction amount,
- risk score,
- failure reason,
- recovery outcome,
- Razorpay response.

All factual information must come from backend tools/data.

---

## 4.3 LangGraph controls workflow

LangGraph should control:

```
START
 ↓
Load Payment
 ↓
Risk Classification
 ↓
Route
 ├── BENIGN
 │      ↓
 │   Diagnose
 │      ↓
 │   Recovery Decision
 │      ↓
 │   Execute
 │      ↓
 │   Verify
 │      ↓
 │   Success / Retry / Escalate
 │
 └── RISKY / UNCERTAIN
        ↓
     Human Review
```

The agent should be stateful.
